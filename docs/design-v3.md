## 0. 一页纸结论

- 这套系统的目标函数 = **在回归基准集（Golden Set）上的通过率 + 失败模式收敛度**。
- 它只对**「高频 × 有量 × 会变」**的流程成立。最优区间：**每天几次到几十次**；≥1000 次/天应当反解 API，本系统不是答案。
- **MVP 只做一个技能，但很多版本。** 横向（技能发现/路由/组合）一律不做。
- MVP 地基五件套：**① 断言分级 ② 元素指纹 ③ 序列对齐 ④ 幂等 ⑤ 断言锚业务单号**。
- 这套系统的天花板是「**稳定地把事做错**」——它只能自愈技术故障，不能判断业务规则是否该变。承认它，用人工复核点兜底。
- **还有第二个天花板：「两次一致」≠「正确」。** 观察里只有一致性，没有对错信号；两遍都点错，它就照着错编译。
- 因此人审有**两道勾**：① 步骤顺序对不对 ② 断言对不对。**只审断言 = 没审。**

## 1. 选型判据：三个轴，不是一个

选第一个技能时，**三个维度都要量**，缺一个就选错：

| 轴 | 定义 | 阈值 |
|---|---|---|
| **频次** | 一天触发几次 | ≥ 5 次/周（低于此学不动） |
| **数量** | 一次处理几条 | 单次 ≤ 约 50 条（更高要上批次模型） |
| **变化率** | 界面/数据/权限会不会变 | 要有变化，否则只是一个贵 cron |

**关键判据：**

- 每天 1–5 次 → 串行 + 人审每个补丁，**MVP 区间** ✅
- 每天 20–50 次 → 并发 + 失败聚合 + 快闸，二期 ⚠️
- 每天 100–1000 次 → 还要灰度/自动回滚/补丁自动放行，二期重活 ⚠️
- **每天 ≥1000 次 → 停。GUI 自动化在经济学上不成立，去反解接口直接调 API。**

**"频次"和"数量"不是一回事：**

- 高频次 × 低数量 → 反复登录开页，核心需求是**保持会话**
- 低频次 × 高数量 → 一次跑很久，核心需求是**断点续跑**
- 高数量 → 一条错不能连坐整批，核心需求是**失败隔离**

**反例数据库（别选这些）：**

| 流程类型 | 为什么不行 |
|---|---|
| 月度报销 | 低频，半年攒不够失败样本 |
| 十年来没动过的内部老系统 | 变化率≈0，Healer 永不触发，等于造贵 cron |
| 一天几千条的批量任务 | GUI 不划算，该上 API |
| 法规强约束、错了要担责的流程 | 见第 6 节天花板，不适合先做 |

## 3. 四条地基 + 一个锚点（MVP 必做）

> **判断"是不是地基"的口诀**：后加它，要不要动已有 schema？要不要重录已有数据？
> 要 → 地基（必须一开始进）；只是多写几个 if → 功能（可以后加）。

### 地基① 断言分级（business / technical）

**为什么是地基**：不分级，Healer 分不清"技能坏了"还是"环境变了"，会去修一个没坏的技能（= 报警器火警和小偷共用一个铃）。

```python
class Assertion(BaseModel):
    assertion_id: str
    kind: Literal["business", "technical"]      # ← 地基①
    anchor: Literal["business_entity", "ui_text"]  # ← 锚点⑤
    operator: Literal["entity_exists","contains","equals",
                      "visible","count_eq","url_match","attr_eq"]
    target: Locator
    expected: Any                # anchor=business_entity 时填单号或正则
    timeout_ms: int = 5000
    confirmed_by: Literal["human", "llm_proposed"]
    source: Literal["observed", "healed_case", "manual_edge"]
    last_verified: datetime
```

- `business` → 进 Golden Set 当判据；Healer 要改它**必须过人**。
- `technical` → 只当**环境探针**；失败只触发"重观察/降级"，**不判技能死**。
- **只有 `confirmed_by="human"` 的断言可以当真值。**

### 锚点⑤ 断言锚在业务实体上，不锚 UI 文案

**为什么是地基级**：UI 文案是整条链最表层的信号。文案变了不代表业务变（判据漂移）；文案出现也不代表业务成了（假成功）。

**规则：**

1. `business` 断言**必须** `anchor="business_entity"`，expected 填**业务单号/流水号/订单 ID**。
2. 只有该流程确实没有业务单号时才降级为 `ui_text`，且必须在 `meta.risk_notes` 里登记。
3. 能回读就回读（`entity_exists` + 单号），别只看提示语。

> 这一条同时干掉"判据漂移"和"假成功"两个风险，是五件套里性价比最高的。

### 地基② 元素指纹

**为什么是地基（最硬的一条）**：指纹必须在**录制那一刻**存下来。MVP 只存 locator 的话，以后想加指纹，**手上没有历史页面数据，只能把所有演示重录**。这是五件套里唯一不可逆的。

```python
class ElementFingerprint(BaseModel):
    role: str
    accessible_name: str
    text_norm: str                       # 归一化文本
    attrs_subset: dict[str, str]         # 除 id 外的稳定属性
    neighbor_text: str                   # 相邻文案（"客户名称"标签）
    bbox_rel: tuple[float, float, float, float]   # 相对位置
    captured_version: str
```

**定位解析顺序（运行时）：**

```
1. 精确 locator
2. 失败 → 指纹加权模糊匹配（role .30 / name .30 / neighbor .20 / text .10 / bbox .10，阈值 ~0.75）
3. 候选 → 提议新 locator
4. 必须用 business 断言验证（改完真提交成功了吗）
```

**收益**：把"环境变"从"上报人"变成"**可自愈且可验证**"。

### 地基③ 两次演示 = 序列对齐

**为什么是地基**：不对齐，变量只能靠 LLM 猜（洞 2），猜错就没人用；而且对齐算法决定 Compiler 的输出结构，后换要重写接口。

**做法（不是 DOM diff，是动作元组序列对齐）：**

```python
tuple = (action_type, role, name_norm, has_value)
# Needleman-Wunsch / LCS 对齐两条序列
```

**对齐结果直接产出四类结论：**

| 情况 | 结论 |
|---|---|
| 对齐 + value 不同 | **变量**（`source="aligned_diff"`） |
| 对齐 + **指纹漂移** | **定位器不稳定** ⚠️ → 标 `fragile=True`，强化指纹（必须按指纹判，不是 selector，见下节 ③） |
| 一侧多出步骤 | 条件分支候选 / 误触噪声（待人确认） |
| 完全一致 | 常量，可硬编码 |

**白捡的预警**：你在**编译期**就知道哪些 locator 会漂，不用等生产环境炸。

### 地基④ 幂等（A1）

**为什么是地基**：所有 RPA 在真实业务里翻车的头号原因，而**"自愈"恰好是它的放大器**——不自愈的脚本只错一次，自愈的脚本会反复错。

**症状链**：提交超时 → Healer 重试 → 第一次其实已成功 → **同一张单提交两次** → 业务侧人工删数据。

```python
class Step(BaseModel):
    step_id: int
    action: Literal["goto","click","fill","select","submit","wait","read_entity"]
    target: Locator
    value: Any | None
    write_effect: Literal["none","create","update","delete","unknown"]   # ← 地基④（unknown 见下节）
    idempotency_key: str | None      # 如 "{{flow_run_id}}::{{record_id}}"
    precheck: Assertion | None       # 重试前先查状态
    assertion: Assertion | None
```

**规则（硬约束，不得绕过）：**

1. `write_effect != "none"` 的步骤**必须**带 `idempotency_key`。
2. **写步骤的重试必须先跑 `precheck`**；precheck 命中（单已存在）→ 跳过，不再提交。
3. 只有 `write_effect == "none"` 的步骤，允许无脑重试。
4. `flow_run_id` 为二期批次模型预留，MVP 单条也要生成。

### 实现期追加：七条硬约束（写代码 + 真浏览器才暴露）

这七条不在第一版设计里，是写 `schema/` / `observer/` / `compiler/` / `executor/` 并接真 Chrome 验证时被逼出来的，**都改到了 schema 或流程层**，所以必须提前冻结。

**① `write_effect` 要有 `unknown`，不能只有四个值。**

```python
write_effect: Literal["none","create","update","delete","unknown"]
```

判定不出来时（按钮文案看不出含义）**必须落到 `unknown`、按写操作对待**，而不是 `none`。原则：

> **默认值的方向决定安全性。** 误判成"更严格"只是麻烦；误判成"更宽松"是事故。

**② `Skill` 要有生命周期状态，否则草稿存不下来。**

编译产物天然全是 `llm_proposed` 断言。如果发布校验和结构校验共用一套，**草稿根本过不了校验**——v3 状态机画了 `HUMAN_REVIEW`，却没有字段承载它。所以拆两层：

```python
state: Literal["draft", "reviewed", "published"] = "draft"

errors()              # 只管结构（草稿也能存）
publish_blockers()    # 发布闸：state == reviewed + 至少一条人确认的 business 断言
```

**③ 不稳定定位（fragile）判定必须用「指纹」，不能用 selector。**

下面表格里"对齐 + target 不同 → 不稳定"，如果 target 只比 selector，三个方向同时出错：

- 录制期不生成精确 selector → 永远判不出不稳定（地基③ 的一半价值归零）
- selector 相同、元素被换了 → 漏判
- selector 不同、只是 id 变了 → 误报

改为：**指纹相似度 < 0.80 → 判 `fragile`**，selector 只作辅助信号。

**④ 联动填充字段：不参数化、不主动回填。**

选"客户"→ 地址被系统自动带出。这个值**不是人填的**。但从"表单快照差集"看不出区别，它会被补录成 fill，甚至被参数化。技能一跑就会往一个本该自动计算的字段里打字。

规则：`source="snapshot_diff"` 的字段

- **不参与参数化**（两次演示值不同也不算入参）
- 编译成 `READ_ENTITY`（只读校验），**不主动填**
- 人审确认"这里确实要人工填"后，才升级成 `fill` + 参数

**⑤ `precheck` 编译器永远生成不出来 → 人审必须有第三道勾。**

写操作硬约束要求「幂等键 + precheck」，但 precheck 是「怎么查这张单是否已存在」——**这是业务知识，编译器不可能知道**。所以草稿必然带一条 error，永远过不了发布闸。

结论：人审从两道勾变**三道勾**：

> **① 步骤顺序对不对 ② 断言对不对 ③ 写操作的 precheck 补了没有**

第三道不补，MVP 的"幂等验证"根本跑不起来——不是代码没写完，是流程里没有这一步。

**⑥ 写操作的定位必须唯一命中。**

真浏览器上 `get_by_role(role, name, exact=False)` 是**子串**匹配。把按钮文案从「提交」改成「提交保存」，定位器**照样命中**——所以"改版"不会失败；更危险的是「提交」可能匹配到**「撤销提交」**，写操作点错一个就出事。

规则：

- 写操作（`write_effect != none`）点击前必须 `count == 1`，否则判 `locator` 失败并拒绝点击。
- 读操作可以宽（子串匹配带来韧性）。

**⑦ `preconditions` 必须由 executor 消费。**

录制器在页面加载**之后**才注入，所以**录不到起始导航**。编译器只能把起始 URL 放进 `preconditions`——但如果执行器不读它，技能就没有起点，全靠调用方自己先去那个页面。

规则：`execute()` 开跑前先处理 `preconditions`：

```python
on_page + locator_or_path  → page.goto(render(url))
check（可选）              → 断言求值，不过则判 env 失败
```

这也顺带给了"环境没就位"一个真正的判据——之前它只存在于设计里。

## 4. Golden Set + 单调性闸

### Golden Set（只增不删）

```python
class GoldenCase(BaseModel):
    case_id: str
    params: dict[str, Any]
    extra_assertions: list[Assertion]
    origin: Literal["demo", "healed_failure", "manual_edge"]
    created_from_version: str
    last_pass_version: str | None
```

三个来源：原始演示（种子）/ 每次自愈修复的失败用例（燃料，永久保留）/ 人工边界用例。

### 单调性闸（v3 的心脏）

新版本 v(N+1) 能否上线，**只看两条**：

```
① 通过率单调：pass_rate(vN+1, Golden) >= pass_rate(vN, Golden)
② 无单点翻转：不存在任何 case，vN 通过而 vN+1 失败
```

- 两条都满足 → 入库发布。
- 任一条不满足 → **拒绝入库，标记回归，补丁退回**。

**这一条闸，是把"越修越坏"挡在门外唯一的东西。** 没有它，Healer 会忠实执行"用一个 bug 换另一个 bug"，成功率曲线原地抖，永远不涨。

### 4.2 自动打补丁（v3.4）

补丁必须走**和人工发版同一条闸**，否则"自动自愈"就退化成"AI 随心改"。三条规则：

1. **只在封闭算子集里搜**，且只应用 `auto_applicable=True` 的算子；
2. **一次只改一个算子**，改完立刻跑 Golden Set 过闸；
3. **没过闸 = 什么都没发生**（`GateRejected` 不写文件），换下一个算子继续试。

两个刻意的限制：

- `dismiss_dialog` **不许自动**：弹窗是录制时没见过的，关哪个按钮只能人指定。
- `swap_locator` 的候选**不能凭空造**：必须从失败页面按元素指纹相似度收集；
  指纹都认不出时，说明变化太大，该走人工。

**真浏览器实测后要补一句反直觉的**：`swap_locator` 的适用窗口比设计时以为的窄得多。

| 相似度 | 结果 |
|---|---|
| ≥ 0.75 | 运行时兜底自己就修好了，**不会失败**，没有补丁可打 |
| 0.5 – 0.75 | 运行时兜不住、但能收集到候选 → 只有这区间才用得上 `swap_locator` |
| < 0.5 | 候选都收不到（文案改版属于此类）→ 只能人工给定位器 |

实测：按钮 `id` 改名（文案不变）→ 相似度 1.00，运行时兜住；
按钮文案「提交」→「确认保存」→ 相似度 < 0.5，候选为空。

> 所以自动自愈的主力应该是 `add_wait` / `drop_optional_step`，
> 不是 `swap_locator`。设计阶段把运行时兜底和补丁算子的阈值当成两件独立的事，
> 实际它们抢同一块地盘。

### 4.3 为什么 Golden Set 要 ≥10 条（修正 v3.0 的说法）

v3.0 写的理由是"3 条太少，一个 case 就是 33 个百分点，闸看不出趋势"。**这个说法不准确。**

真正的问题是**覆盖面**，不是分辨率：闸只能拦住**已经存在的用例**的退化。
3 条集里没有"7 位单号"这种用例，那么"把正则从 `R\-\d{6,}` 收紧成 `R\-\d{8}`"这种回归
**压根不会被发现**，闸会愉快放行。

> 正确理由：**你想要的用例得先存在，闸才能拦住它。** 分辨率是顺带的。

`golden/suggest.py` 从参数定义生成候选用例（单参数扰动），但**全部标 `origin="manual_edge"`**——
生成用例解决的是"人懒得想"，不是"自动获得真值"。人不确认，它会污染闸。

### 4.4 technical 探针的累积告警（v3.5）

单次 `technical` 失败**不判死**是对的——它只是环境探针。但同一个探针连续响 20 次，
说明环境真的变了，之前却没有任何机制喊一声，这就是**静默退化**。

规则：

- 按断言累计**连续失败**次数，落盘；连续 ≥ 阈值（默认 5）→ 升格，只在跨过阈值那一次报
- 成功一次 → 清零并清掉升格标记（复发能重新升格）
- **只升格、不自动改技能**。这里只负责喊，人是最后一道闸

> 为什么不自动改：technical 断言本身就是"环境可能变了"的信号，
> 拿它当依据去改技能，等于把"环境变了"误判成"技能错了"。

## 5. 闭环状态机

```
IDLE
 └─▶ OBSERVING               录 2 次演示（带状态快照 + 元素指纹）
     └─▶ ALIGNING            序列对齐 → 变量 / fragile locator / 分支候选
         └─▶ COMPILING        生成 Skill + 断言清单（llm_proposed）
             └─▶ HUMAN_REVIEW 人打**三道勾**：① 步骤顺序 ② 断言 ③ 写操作 precheck
                 │             ★ 只审断言 = 没审（见 6.2 天花板二）
                 │             ★ business 断言必须是业务单号
                 │             ★ precheck 编译器生成不出来，只能人补
                 │             ★ 三道勾全 True → Skill.state: draft → reviewed
                 └─▶ EVALUATING 在 Golden Set 上跑候选版本
                     └─▶ GATE（单调性）
                         ├─ 通过 → 发布 vN+1
                         └─ 不通过 → 拒绝入库，标记回归
 └─▶ RUNNING                 业务执行
     ├─ 成功 → 记录
     └─ 失败 → TRIAGE（三层定位）
               ├─ 参数错 → coerce_param（二期算子集）
               ├─ 步骤错 → swap_locator / add_wait（二期算子集）
               ├─ 环境变 → 指纹重匹配 → 重验证（MVP 就要能走这条）
               └─ 不可修 → 人工接管
               └─▶ 用例入 Golden Set → 回到 EVALUATING
```

**注**：状态机是完整目标。MVP 只要求能走通 `OBSERVING → HUMAN_REVIEW → EVALUATING → RUNNING → 环境变修复 → GATE → v1.1` 这一圈。

## 6. 产品边界（必须写进产品，不是写进 README 角落）

### 6.1 天花板：它会"稳定地把事做错"

自愈只修**技术**问题，修不了**业务规则**变更。

政策变了、字段含义变了，系统不会停——它会把这个**已经错了的流程执行得又快又稳，成功率 100%**。Golden Set 全是历史用例，天然验证不了"现在还该不该这么做"。

**你越优化，它错得越稳。** 这不是 bug，是这类系统的性质。

**处置（三件，缺一不可）：**

1. **人工复核点**：按风险分级设置强制停下等人的位置
   - 金额 > 阈值 → 必人审
   - `write_effect = delete` → 必人审
   - 新增/删除步骤 → 必人审
   - business 断言变更 → 必人审
2. **业务哨兵清单**：登记"哪些字段/规则一旦变化必须停下来问人"，写进 Skill 的 `meta.watch_fields`。
3. **对外口径**：不承诺"全自动"，承诺"**技术性重复劳动的自动化 + 业务变更的人工闸**"。

### 6.2 天花板之二：「两次一致」不等于「正确」

序列对齐只能证明两遍演示**一样**，不能证明两遍**对**。

人在两遍里都点错同一个按钮，对齐会判"这就是标准流程"，照单编译。更糟的是——**Golden Set 的三条也来自这批演示，同一个盲区一路贯穿到底**：编译错、基准错、验收也错，而系统还会告诉你"3 条全过"。

> 这是"从观察学习"这件事的天花板：**观察里没有对错信号，只有一致性。**

**处置（只有一条，但必须硬执行）：**

> **人审必须打三道勾：① 步骤顺序对不对（"这五步是不是你要的流程"）② 断言对不对 ③ 写操作 precheck 补了没有。**
> 只审断言 = 没审。三道勾都打完，才允许 `draft → reviewed`。

### 6.3 能力上限

- 每天 ≥1000 次 → 本系统不是答案，去反解 API。
- 单次 > 约 50 条 → 需要二期批次模型（断点续跑/失败隔离/批量幂等）。

## 7. MVP 验收标准（可逐条打勾）

只做一个技能，以下 14 条全过才算 MVP 完成：

- [ ] 1. 录一个**日频**流程，2 次演示，**参数必须不同**
- [ ] 2. 对齐报告产出 ≥1 个变量（`source="aligned_diff"`）
- [ ] 3. **变量数 = 0 直接判失败**：说明两次演示没换参数，产出的会是硬编码假技能（静默失败，最危险）
- [ ] 4. 若两次演示 target 漂移 → 产出 ≥1 条 `fragile` 预警（按指纹判定，不是 selector）
- [ ] 5. **步骤清单由真人逐条打勾**："这五步就是我要的流程，顺序也对"（6.2 天花板二的第一道防线）
- [ ] 6. 断言清单 ≥2 条，全部 `confirmed_by="human"`
- [ ] 7. 其中 ≥1 条 `business` + `anchor="business_entity"`（业务单号）
- [ ] 8. **每个写步骤都补了 `precheck`**（"怎么查这张单已存在"）——编译器生成不出来，只能人补
- [ ] 9. `review_checklist()` 三道勾全 True，`Skill.state` 从 `draft` → `reviewed`
- [ ] 10. Golden Set 建成 3 条（2 演示 + 1 人工边界）
- [ ] 11. 人为制造 1 次环境失败（改 locator）→ 定级为"环境变"（`failure_layer=locator`），**不是**误判成业务失败
- [ ] 12. 修复后 v1.1：Golden Set 3 条全过 **且** 无单点翻转
- [ ] 13. **幂等验证**：故意让提交超时触发重试 → 业务侧只产生 **1 条**记录
- [ ] 14. 回滚：一条命令退回 v1.0

> **第 3、8、13 条是必测项**，不过不算完成：
> 第 3 条挡"编译期不报错、第一次换客户才崩"；第 8 条挡"写操作没有查重就敢跑"；第 13 条挡"线上第一次事故就是重复提交"。

## 8. 二期清单（不动地基，纯加法）

| 编号 | 条目 | 为什么二期 |
|---|---|---|
| ④ | **修复算子封闭集**（swap_locator / add_wait / coerce_param / drop_optional_step / dismiss_dialog，带前条件+代价，一次只改一个） | Healer 内部实现，不改 schema |
| ⑤ | **扰动探测**（删步/换序 → 看业务断言 → 反推"为什么"+ 压成最小技能） | Compiler 后处理，schema 不动 |
| ⑥ | **失败模式覆盖率**（failure_taxonomy + coverage，作为第二目标函数） | meta 加统计字段 |
| A2 | **失败聚类**（按 失败步+错误特征+断言签名，每类只 heal 一次） | 高数量场景必需，MVP 单条用不上 |
| B2 | **变异测试**（故意注入坏 locator/删步/换参，检查 Golden Set 抓不抓得住） | 给闸本身做体检，MVP 先用人工抽查 |
| C1 | **批次模型**（断点续跑 / 失败隔离 / 批量幂等） | 单次 >50 条才需要 |
| C2 | **补丁风险分级**（低风险自动放行，改业务断言/增删步必须人审） | 每天 >20 次才成瓶颈 |
| C3 | **灰度 + 自动回滚** | 每天 >100 次才需要 |
| C4 | **并发隔离**（独立 context / 账号 / 冲突资源串行） | 并发才需要 |
| C5 | **异步轮询断言**（业务级，分钟级超时） | 有异步后台处理才需要 |
| C6 | **凭证脱敏**（Trace 脱敏，DSL 只存 `{{secret:xxx}}` 引用） | 上线前必做 |

## 10. 一句话施工令

> **先做「一个日频、每天几十次、会变」的技能，把它从 v1.0 推到 v1.1 且 Golden Set 不退化为止。**
> 这五件地基（断言分级 / 元素指纹 / 序列对齐 / 幂等 / 锚单号）不进，后面 Executor 和 Healer 全部返工；这五件进了，二期全是加法。
